## Файлы

Остальные файлы и коллекции не удалять. Сделать commit и дождаться GitHub Pages.

## Схема Firestore

`payment_requests/{requestId}`:
- `uid`: string — Firebase Auth UID заявителя
- `name`: string
- `group`: string
- `amount`: number
- `days`: number
- `status`: `pending`, `approved`, `rejected` или `revoked`
- `createdAt`: Firestore Timestamp
- `approvedAt`: Firestore Timestamp (после одобрения)
- `approvedExpiresAt`: number, Unix milliseconds (после одобрения)
- `approvedProfileId`: string (после одобрения)

`users/{normalizedName}__{normalizedGroup}`:
- `uid`: string
- `name`: string
- `group`: string
- `premiumActive`: boolean
- `premiumExpiresAt`: number, Unix milliseconds
- `updatedAt`: Firestore Timestamp

Не создавай коллекции заново и не удаляй документы. Firestore не требует заранее объявлять поля — они добавляются при записи.

## Для исправления старой одобренной заявки Антона
После установки открой админ-панель → «Активированные» → у заявки Антона нажми «Синхронизировать профиль». Эта операция использует существующий `approvedExpiresAt` и не добавляет ещё 30 дней. Проверь, что UID заявки совпадает с UID пользователя.

Если профиль пользователя отсутствует, код может создать документ по нормализованному ID только когда нет конфликтующего профиля. При неоднозначных профилях операция останавливается и показывает ошибку.

## Индексы
Новая версия не использует `orderBy` в Firestore-запросах заявок, поэтому для списка pending/approved composite index не нужен. Поиск профиля по `uid` использует одиночное поле.

## КРИТИЧЕСКИ ВАЖНО: Firestore Rules
Не вставляй правила вслепую и не делай базу публичной. В текущем репозитории файл `firestore.rules` не найден, поэтому фактические правила проекта неизвестны.

Правила должны:
1. Разрешать чтение/изменение `payment_requests` администратору только если `request.auth != null` и `get(/databases/$(database)/documents/roles/$(request.auth.uid)).data.role == 'admin'`.
2. Разрешать пользователю создавать только свою заявку: `request.resource.data.uid == request.auth.uid`, `status == 'pending'`, а поля суммы/дней/времени и approved-поля должны быть ограничены.
3. Запрещать обычному пользователю изменять `premiumActive`, `premiumExpiresAt`, `uid` и роль в профиле `users`.
4. Запрещать клиенту менять собственный документ `/roles/{uid}` на admin.
5. Учитывать текущие правила для `topics`, редакторов и остальных функций DORO — не заменять их неполным набором.

Админ-проверка в JavaScript нужна только для интерфейса; безопасность обеспечивают Firestore Rules. Если правила сейчас блокируют операции, интерфейс покажет конкретную ошибку.

## Проверка после установки
1. Открыть админ-панель и проверить загрузку заявок.
2. Для старой одобренной заявки Антона нажать «Синхронизировать профиль».
3. Убедиться в `users/антон__лд2511`, что `premiumActive` = true и `premiumExpiresAt` — Number с будущим Unix-временем в миллисекундах.
4. Создать тестовую заявку на тестовом аккаунте и одобрить её.
5. Проверить, что повторное нажатие «Синхронизировать профиль» не увеличивает срок.
6. Проверить отзыв подписки и наличие другой одобренной заявки до отзыва: другой действующий срок должен сохраниться.

## Важно про серверную защиту
Этот пакет исправляет клиентский workflow, но не делает клиентскую активацию серверно-доверенной сам по себе. Для более строгой защиты от подмены полей лучше перенести одобрение в Cloud Function/серверный endpoint, доступный только администраторам. Не хранить секреты в JavaScript на GitHub Pages.


## Диагностика конфликтов профилей (исправление UID)
Новая версия admin.js сначала ищет users по точному UID заявки и не смешивает найденный документ с историческими ID по имени/группе. Если поиск по UID находит ровно один профиль, используется именно он. Если найдено несколько документов с одним UID, интерфейс покажет их ID. Если UID-поиск ничего не нашёл, код проверит старые ID, но не перезапишет существующий документ с другим или отсутствующим UID.
